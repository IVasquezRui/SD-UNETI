    Paso 01

    Elegir la topología

    La misma aplicación admite tres formas de montaje. La recomendada es Docker Compose sobre una VM; las otras dos cubren restricciones institucionales.

    RutaCuándo usarlaComplejidadReproducibilidad
    A · DockerCaso normal; actualización por imagenMediaAlta
    B · NativoNo se permite DockerAltaMedia
    C · HíbridoWordPress en Docker y Next nativoMedia-altaMedia
    LXCAhorro de recursosMediaMedia

    Recomendación: VM Debian 13 de 4 vCPU y 8 GB, Docker Compose para el stack y Caddy en el host como proxy TLS. Caddy dentro de Docker no ve la IP real del cliente y rompe las reglas de Tailscale y de wp-admin.

    Paso 04

    Preparar Proxmox

    Crear la VM con Debian 13, IP fija y agente invitado. Antes de instalar nada, tomar un snapshot y un respaldo del hipervisor.

    qm create 210 --name uneti-prod --memory 8192 --cores 4 --sockets 1 \
  --net0 virtio,bridge=vmbr0,tag=10 \
  --scsihw virtio-scsi-pci --scsi0 local-lvm:100 \
  --ide2 local:iso/debian-13-netinst.iso,media=cdrom \
  --boot order=scsi0 --ostype l26 --agent enabled=1
qm start 210

# Red dentro de la VM
ip -4 addr show
ip route
ping -c 3 1.1.1.1 && curl -I https://deb.debian.org

# Snapshot y respaldo antes de tocar el sistema
qm snapshot 210 antes-de-instalar-docker
vzdump 210 --storage backup --mode snapshot --compress zstd

    Programar vzdump diario en Datacenter → Backup con retención de 7 diarios y 4 semanales.

    Ruta A · Docker

    Build inmutable y compose de producción

    Crear frontend/Dockerfile y deploy/compose.prod.yml. El compose de producción publica solo en loopback y deja la base sin puerto.

    FROM node:26.13.0-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --no-audit --no-fund

FROM node:26.13.0-slim AS build
WORKDIR /app
ARG NEXT_PUBLIC_SITE_URL
ENV NEXT_PUBLIC_SITE_URL=$NEXT_PUBLIC_SITE_URL
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

FROM node:26.13.0-slim AS runner
WORKDIR /app
ENV NODE_ENV=production PORT=3000
RUN groupadd --system uneti && useradd --system --gid uneti --create-home uneti
COPY --from=build --chown=uneti:uneti /app/.next ./.next
COPY --from=build --chown=uneti:uneti /app/public ./public
COPY --from=build --chown=uneti:uneti /app/package.json ./package.json
COPY --from=build --chown=uneti:uneti /app/next.config.ts ./next.config.ts
COPY --from=build --chown=uneti:uneti /app/node_modules ./node_modules
USER uneti
CMD ["npm", "run", "start"]

    NEXT_PUBLIC_SITE_URL se fija en el build: pasarla como args del compose o con --build-arg. Si se define solo al ejecutar, sitemap.xml y los metadatos quedan mal.

    El compose completo (servicios db, wordpress y frontend, healthchecks, límites y logs) está en el documento Markdown, sección 5.5.

    Ruta A · Docker

    Arranque y seed

    cd /srv/uneti/app
COMPOSE="docker compose --env-file .env -f deploy/compose.prod.yml"

$COMPOSE build
$COMPOSE up -d
$COMPOSE ps          # los 3 servicios deben quedar healthy

python3 scripts/seed/seed.py bootstrap --project uneti-prod --service wordpress
python3 scripts/seed/seed.py verify   --project uneti-prod --service wordpress

    Qué hace el bootstrap

    1. Instala WordPress si la base está vacía.
    2. Activa WPGraphQL.
    3. Importa los fixtures de seed/ con las APIs nativas.
    4. Verifica GraphQL, comentarios e imágenes.

    seed.py usa docker compose -p uneti-prod. El nombre del proyecto debe coincidir con name: del compose y con COMPOSE_PROJECT_NAME.

    Paso 09

    Backups y restauración

    Backup diario de base de datos y wp_data, cifrado con age, retención de 14 días y copia fuera del host.

    # Docker
docker compose --env-file .env -f deploy/compose.prod.yml exec -T db sh -c \
  'exec mariadb-dump --single-transaction --quick --routines --triggers \
   -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"' | gzip -9 > db.sql.gz
tar -C /srv/uneti/data -czf wp.tar.gz wp
age -r "$AGE_RECIPIENT" -o db.sql.gz.age db.sql.gz
age -r "$AGE_RECIPIENT" -o wp.tar.gz.age  wp.tar.gz
rsync -a /srv/uneti/backups/ backup@nas.dominio:/backups/sd-uneti/

# Respaldo del hipervisor
vzdump 210 --storage backup --mode snapshot --compress zstd \
  --prune-backups keep-daily=7,keep-weekly=4,keep-monthly=12

    Prueba de restauración (trimestral)

    age -d -i /root/age.key -o /tmp/db.sql.gz /srv/uneti/backups/db-FECHA.sql.gz.age
gunzip -c /tmp/db.sql.gz | docker compose --env-file .env -f deploy/compose.prod.yml \
  exec -T db mariadb -uroot -p"$MYSQL_ROOT_PASSWORD" wordpress_db

    Un backup que no se restaura no es un backup. Registrar fecha, responsable, archivo restaurado y resultado.
